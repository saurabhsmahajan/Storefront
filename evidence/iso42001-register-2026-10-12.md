   # ISO/IEC 42001 AI system register and risk register: Storefront support agent (2026-10-12)

   ## Status and scope

   - A project-level register for a portfolio build, aligned to ISO 42001 concepts.
     It is not a certified AI management system. No organisation-wide management
     system, scope statement or Statement of Applicability exists here, and nothing
     in this file claims conformity.
   - Annex A references are at objective level (A.3 to A.10). Sub-controls A.3.2,
     A.5.4, A.5.5 and A.9.4 are named because the secondary sources agree on them.
     Those sources paraphrase other control titles differently. Check the official
     text before citing a sub-control in anything formal.
   - Owner: Saurabh Mahajan (project owner). Review: Week 5 revisits this file.
   - Lifecycle: built and verified in Week 2. No production traffic. Not deployed
     to real customers.

   ## 1. AI system register

   Common to every entry:
   - Supplier and model (A.10): Anthropic Claude through the API. One model constant
     for every component, claude-sonnet-5-5 (agents/config.mjs). The supplier's terms
     and data-processing terms have not been reviewed as part of this project.
   - Owner (A.3.2): the project owner, accountable for design, evidence and review.
   - Human oversight: every refund is decided by a human. Code, not the model,
     decides every escalation. Every escalation carries a validated handoff package
     that says nothing is approved (refund_approved false).
   - The orchestration layer is code, not AI, and is treated as the control
     environment: agents/system/dispatch.mjs, agents/lib/loop.mjs (step cap, forced
     escalation), escalation-rules.mjs, handoff.mjs, combine.mjs, merge.mjs,
     run-plan.mjs. 112 tests pass.

   ### SYS-01 Router (classifier)
   - Intended use (A.9.4): choose which specialist handles a customer message.
     Code decides the human-request, no-label and out-of-scope paths from its label.
   - Code: agents/layer2/classify.mjs, used by agents/system/dispatch.mjs.
   - Input and output: the customer message in, one label out (order_status,
     decline, refund, human_request, out_of_scope). Anything outside the fixed list
     is treated as no label and escalates.
   - Data and credentials (A.7): none. It holds no customer data and no database
     credential.
   - Failure behaviour: bounded by routerTimeoutMs (30 s). A failure or timeout is a
     router failure and escalates with api_error.
   - Impact (A.5.4): a wrong label sends a customer to the wrong specialist. A wrong
     human_request or out_of_scope label could delay help.
   - Risk tier: medium. It is the control point for every message.
   - Verification (A.6): evidence/router-comparison-2026-10-06.md (21 of 21 against
     an answer key written first), evidence/failure-injection-router-summary-2026-10-12.md.
   - Known limits: labels for borderline messages can vary between runs, because
     this model does not accept a temperature setting.

   ### SYS-02 Planner (decomposition)
   - Intended use: split a message that clearly asks for different things into
     subtasks. Single-intent messages stay as one.
   - Code: agents/layer2/planner.mjs, plan-prompt.txt (v1, frozen),
     agents/lib/plan.mjs (validator).
   - Output must pass validation in code: 1 to 3 subtasks, allowed specialists only,
     every question a verbatim span of the customer's message, order IDs referenced
     by index, unknown keys rejected.
   - Data and credentials: none. The planner is optional. A missing, failed,
     timed-out or invalid plan falls back to the single path.
   - Impact: a bad split can drop half of a mixed question, or hand a specialist a
     question it must decline.
   - Risk tier: medium.
   - Verification: evidence/planner-dry-run-v1-2026-10-06.md (criteria written before
     the run), evidence/system-decompose-scores-2026-10-06.md,
     evidence/system-v2-check-scores-2026-10-06.md.
   - Known limits: findings D1, D2 and D4 (a contradictory reply on #17, and a split
     that varied between runs). One run per message.

   ### SYS-03 Order Status specialist
   - Intended use: tell a customer the state of one order: status, total, date, age.
   - Data and credentials (A.7): reads orders only, through the order_status
     credential. Payment events return no rows. Tool: get_order_status.
   - Oversight: no write access (evidence/credential-denial-2026-10-06.md).
   - Impact (A.5.4): a wrong status could mislead a customer about payment or
     delivery. It cannot see shipping or tracking, and says so.
   - Risk tier: low to medium.
   - Verification: evidence/order-status-check-2026-10-06.md,
     evidence/specialist-credential-real-signin-2026-10-06.md.
   - Known limits: 3 of 6 order-status test messages correct in the full system run.
     It cannot answer "where is it", and cannot see payment context, by design
     (evidence/jtbd-and-rice-2026-10-12.md).

   ### SYS-04 Decline Explainer
   - Intended use: explain why a card payment did not go through, at the level the
     disclosure rule allows.
   - Data and credentials: reads payment_events only, through the decline credential.
     No orders.
   - Controls: the disclosure rule is applied in code (evidence/decline-disclosure-
     decision-2026-10-06.md). The model receives only approved text. Raw refusal
     reasons never reach it, and are kept for the human handoff.
   - Impact (A.5.4): disclosing fraud-screening detail or the failed card field helps
     card testing. A wrong explanation sends the customer to the wrong fix.
   - Risk tier: medium to high (security-sensitive).
   - Verification: evidence/decline-explainer-check-2026-10-06.md, failure injection
     row I5 (evidence/failure-injection-summary-2026-10-12.md).
   - Known limits: a reason not in the mapping defaults to never_tell. The mapping
     needs a periodic check against Adyen's refusal-reason documentation.

   ### SYS-05 Refund Eligibility specialist
   - Intended use: check whether an order can be refunded, explain the result, and
     recommend to a human. It cannot issue or approve a refund.
   - Data and credentials: reads orders and payment_events through the refund
     credential. Raw payment events never reach the model: the tool returns only a
     verdict, a reason code and facts.
   - Controls: eligibility is decided by tested code (agents/lib/refund-rules.mjs,
     13 tests, 30-day window, day 30 eligible and day 31 not). No tool executes a
     refund. Code escalates eligible and no-rule verdicts. The package validator
     rejects any package that claims approval.
   - Impact (A.5.4): financial. A wrong eligibility answer or an implied promise
     affects a customer's money.
   - Risk tier: high.
   - Verification: evidence/refund-specialist-check-2026-10-06.md,
     evidence/handoff-and-escalation-2026-10-06.md, evidence/system-scores-2026-10-06.md.
   - Known limits: the policy has a deliberate gap (a cancelled order that was
     authorised). It returns no_rule and escalates.

   ## 2. Risk register

   Scale: likelihood 1 (rare) to 5 (expected), impact 1 (minor) to 5 (severe),
   score = likelihood x impact. Bands: 1 to 4 low, 5 to 9 medium, 10 to 14 high,
   15 to 25 critical. The ratings are the project owner's draft judgements from the
   evidence cited. The residual rating assumes the controls work as tested.

   | ID | Risk | Inherent | Residual | Band |
   |---|---|---|---|---|
   | R-01 | Invented facts about orders or payments | 4x4 = 16 | 2x3 = 6 | medium |
   | R-02 | Disclosure of fraud-screening detail or card fields | 4x4 = 16 | 1x4 = 4 | low |
   | R-03 | A refund approved or promised without a human | 3x5 = 15 | 1x5 = 5 | medium |
   | R-04 | Anyone with an order ID can retrieve that customer's order data | 4x5 = 20 | 4x5 = 20 | critical |
   | R-05 | Prompt injection or instruction override | 4x4 = 16 | 2x4 = 8 | medium |
   | R-06 | A session that never ends | 4x3 = 12 | 1x3 = 3 | low |
   | R-07 | A wrong answer after a tool error, with no escalation | 3x4 = 12 | 2x4 = 8 | medium |
   | R-08 | Dependence on one third-party model | 3x4 = 12 | 3x3 = 9 | medium |
   | R-09 | Escalations that nobody receives | 5x4 = 20 | 5x4 = 20 | critical |
   | R-10 | Inconsistent splits and contradictory merged replies | 4x2 = 8 | 3x2 = 6 | medium |
   | R-11 | Card-related data in stored events, logs and evidence | 3x4 = 12 | 2x4 = 8 | medium |
   | R-12 | Claims that outrun the evidence | 4x3 = 12 | 3x3 = 9 | medium |
   | R-13 | The customer is not told they are talking to an AI system | 5x2 = 10 | 5x2 = 10 | high |

   ### R-01 Invented facts about orders or payments (A.5, A.6)
   - Evidence: Layer 1 (no tools) invented in 2 of 21 messages (#8, #10: "you won't be
     billed", with no data). Layers 2, 3 and the full system invented in 0 of 21
     (evidence/layer-comparison-2026-10-06.md).
   - Controls: facts come only from tools. Specialists are told to state only tool
     results. The refund decision is code. An empty reply and repeated tool errors
     escalate.
   - Treatment: a live check with a real model after tool failures (I6b). Re-score
     on any model change (R-08).

   ### R-02 Disclosure of fraud-screening detail or card fields (A.5, A.7, A.9)
   - Evidence: Layers 2 and 3 revealed "FRAUD" and "Acquirer Fraud" (#9, #10). The
     full system showed no leak on #9, #10 or X5.
   - Controls: the disclosure mapping is applied in code before the model sees the
     events. Unknown reasons default to never_tell. In failure row I5, four odd events
     all produced the generic text and no raw reason reached the model. Raw reasons go
     to the human package only.
   - Treatment: unit tests for the mapping. A periodic check against Adyen's
     refusal-reason documentation.

   ### R-03 A refund approved or promised without a human (A.6, A.9)
   - Evidence: in Layer 3 the model decided escalation, and a reply said the human
     "will approve" the refund (finding S3, fixed).
   - Controls: no tool executes a refund. Eligibility is tested code. Code decides
     escalation. The package validator rejects a package that claims approval, and a
     caller cannot set the authorisation state (handoff tests).
   - Residual: the model's free text could still imply approval. Code does not scan
     replies.
   - Treatment: write the customer-facing refund sentence in code, or scan for
     approval wording.

   ### R-04 Anyone with an order ID can retrieve that customer's order data (A.5.4, A.7, A.9)
   - Evidence: the specialist credentials read every customer's orders. The chat
     accepts any order ID typed into it. The disclosure decision records the chat as
     unauthenticated in effect. The credential tests show read-only, per-table scoping
     but no per-customer scoping (evidence/credential-denial-2026-10-06.md).
   - Controls: read-only credentials per specialist. UUID order IDs are hard to guess,
     which is not a control.
   - Treatment: bind the session to the signed-in customer and scope reads to that
     customer's own orders before any real customer uses this.
   - Status: open. Blocks production.

   ### R-05 Prompt injection or instruction override (A.6, A.9)
   - Evidence: #21 and X4 held in every layer. In the full system the injected text
     reaches only the classifier (one label out) or a specialist with no refund tool.
   - Controls: no refund tool. The classifier output is one label from a fixed list.
     The planner may only copy spans of the message. Code owns escalation.
   - Residual: two test messages only. Injected text inside a specialist's input is
     not scanned.
   - Treatment: a broader injection test set.

   ### R-06 A session that never ends (A.6)
   - Evidence: I1 (single-path hang) and I12a to I12c (classifier and planner) were
     found and fixed (evidence/failure-injection-summary-2026-10-12.md and
     evidence/failure-injection-router-summary-2026-10-12.md).
   - Controls: step cap of 6, a 60 s specialist limit, a 30 s router limit, forced
     escalation, 112 tests, and the injection scripts.
   - Residual: a timed-out call is not cancelled (I13). The bound of about 90 s is
     derived from the code, not measured as one run.
   - Treatment: abort signals on model calls.

   ### R-07 A wrong answer after a tool error, with no escalation (A.6)
   - Evidence: failure row I6. Two tool errors escalate. A single tool error does not
     (I6b), and the raw exception text is passed to the model (I6a).
   - Controls: the two-error rule, empty-reply escalation, scripted tests.
   - Treatment: a live check with a real model. Replace tool error text with a generic
     message. Consider escalating on a first error for money-related tools.

   ### R-08 Dependence on one third-party model (A.10)
   - Evidence: one model constant for every component. The model rejected the
     temperature setting during the classifier build. API errors (I9 to I11) escalate.
   - Controls: the model is set in one place, and every API failure ends in an
     escalation.
   - Treatment: re-run the 21 messages and the failure injection on any model change.
     Review the supplier's terms. Run files record the model name.

   ### R-09 Escalations that nobody receives (A.3.2, A.9)
   - Evidence: finding G5. Packages are built and validated but are written only to
     run files. "to: human" is a label.
   - Controls: the package structure only.
   - Treatment: a queue or ticket integration with an owner and a response target.
     Until then, do not tell customers that a human will pick it up.
   - Status: open. Blocks production.

   ### R-10 Inconsistent splits and contradictory merged replies (A.6)
   - Evidence: findings D1, D2, D4, D7 (evidence/system-decompose-scores-2026-10-06.md).
     #17's reply contradicted itself. A split varied between runs. D6 was fixed (v2).
   - Controls: an invalid or single-subtask plan falls back to the single path. The
     single-intent path is unchanged, byte for byte (tests).
   - Treatment: planner v2 and a fresh 21-message dry run.

   ### R-11 Card-related data in stored events, logs and evidence (A.7)
   - Evidence: payment events store an authorisation code, the last four digits and
     the expiry in one field (seeded with fake values here). Layer 3's run files
     logged raw tool results that contained them.
   - Controls: the current tools return mapped text or facts only. Secrets are in
     .env, which git ignores and Claude Code is denied from reading.
   - Treatment: retention and redaction rules before any real data. Check that run
     files never log raw events.

   ### R-12 Claims that outrun the evidence (A.6)
   - Evidence: a 21-message hand-scored set, one run per layer. The expectations for
     #7 to #10 were revised during the work. The failure instruments are scripted.
   - Controls: predictions written before runs, raw runs committed before scoring, a
     before, control and after run for each fix, and limits stated in every file.
   - Treatment: re-score on any change. A larger set and repeated runs.

   ### R-13 The customer is not told they are talking to an AI system (A.8)
   - Evidence: replies say "I'm passing you to a human agent", and nothing tells the
     customer that they were talking to an AI system.
   - Controls: none.
   - Treatment: a fixed disclosure line at the start of a session, written by code.
